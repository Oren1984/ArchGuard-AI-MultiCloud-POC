# ADR 0002: PostgreSQL persistence, never SQLite for verification

## Status

Accepted

## Context

The spec mandates PostgreSQL persistence for operational events, risk assessments, AI
recommendations, evaluation results, approvals, audit logs, kill-switch state, and
provider-eligibility records, and explicitly says: "Do not use SQLite as a silent
replacement for required PostgreSQL integration tests."

## Decision

Use PostgreSQL as the only supported persistence target, via SQLAlchemy 2.0 + Alembic
migrations + `psycopg` (v3). Use PostgreSQL-specific column types where they materially
help (`JSONB` for structured evidence/details/triggered-rules; `Identity()` for a
monotonic audit-sequence column independent of UUID ordering) rather than
lowest-common-denominator types that would keep the door open to SQLite. Test-suite
isolation is achieved through per-test transactions rolled back on teardown (real
PostgreSQL, fast), not through swapping in an in-memory database.

## Consequences

- Repository and integration tests exercise real `CHECK` constraints, `ON DELETE CASCADE`,
  and `JSONB` behavior — bugs that a SQLite stand-in would hide (e.g., SQLite doesn't
  enforce `CHECK` constraints exactly the same way, doesn't have a real `JSONB` type) are
  caught.
- Local development and CI both require an actual PostgreSQL instance (Docker Compose
  locally, a service container in CI) — a small extra step, accepted deliberately.
- The Alembic migration is hand-written to exactly match the ORM models rather than
  autogenerated against a live database at development time, keeping migration authorship
  decoupled from having Postgres running while iterating on models — verified after the
  fact via `tests/integration/test_migrations.py` running real upgrade/downgrade cycles.
